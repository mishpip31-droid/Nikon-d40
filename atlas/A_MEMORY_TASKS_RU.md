# Nikon D40: задача памяти A и зависимость запуска, v10

Исследован **AD400112.bin**, SHA-256 `0cc92921d6b2ad5d5cfa070abeebdd9aaca224d326e42a26339e3ac384270394`. Все адреса относятся к **A 1.12**, не к B и не автоматически к A 1.11. Дата: 28 октября 2026 года.

Установлена связь: **задача 1 → запрос через почтовый ящик 1 → задача 5 → уведомление через группу событий 3**. В начальной ветви задача 1 читает 1024 байта в RAM и проверяет первые 896 байтов. Задача 5 обслуживает протокол чтения/записи последовательной памяти, характерный для SPI EEPROM. Она не подтверждена как канал A–B.

Проверки выполнялись на оригинальных инструкциях с явно заданными моделями передачи байтов, событий ОС и задержек. Физическая память, прерывания, параллельное планирование и камера не эмулировались целиком. Новой прошивки для установки этот этап не создаёт.

## 1. Что делает задача 5

Вход `0xD4622`, цикл получения сообщения `0xD463A`.

| Этап | Действие оригинального кода |
|---|---|
| Получение | `rcv_msg`, почтовый ящик 1; указатель результата в r13 |
| Разбор | Четыре 16-битных поля сообщения копируются в `0x3D508…0x3D50E` |
| Допуск | Ожидание группы событий 2, маска `0x4000`, затем сброс этого бита |
| Выбор | Бит 15 первого поля: 0 — запись, 1 — чтение |
| Операция | Настройка передачи, опрос состояния, чтение либо запись порциями |
| Завершение | Отключение настроенной передачи, возврат бита `0x4000` группе 2, установка запрошенной маски группе 3 |

Начальный участок задачи 1, `0xC0F1E…0xC0F6E`, устанавливает бит `0x4000` группы 2. Этот участок выполнен отдельно с регистрацией вызовов ОС. Таким образом, найден конкретный программный допуск для работы задачи 5; семантика остальных событий этой ветви пока не восстановлена полностью.

### Сообщение в почтовом ящике

| Смещение | Размер | Значение |
|---|---:|---|
| `+0x00`, `+0x04` | по 4 | В исследованных отправителях обнуляются; служебная часть сообщения |
| `+0x08` | 2 | Адрес и направление: старший бит выбирает чтение, при передаче адреса он удаляется |
| `+0x0A` | 2 | Младшие 16 бит адреса RAM; обработчик добавляет биты `0x30000` через OR |
| `+0x0C` | 2 | Длина |
| `+0x0E` | 2 | Маска уведомления в группе событий 3 |

Наблюдаемое 15-битное адресное поле **не устанавливает физическую ёмкость микросхемы**. Диапазоны допустимых запросов всех отправителей не восстановлены.

### Команды и разбиение записи

Код формирует команды `05` для чтения состояния, `06` для разрешения записи, `01 00` для записи нулевого состояния, `02 адрес_hi адрес_lo` для записи и `03 адрес_hi адрес_lo` для чтения. При формировании адреса `адрес_hi &= 0x7F`.

Набор команд и 32-байтное разбиение согласуются с классом SPI EEPROM. Для сравнения использовано первичное [описание Microchip 25AA640/25LC640, таблица 3-1 и раздел 3.3](https://ww1.microchip.com/downloads/en/DeviceDoc/21223f.pdf). **Это не идентификация установленной в D40 микросхемы.** Такой набор команд используется разными устройствами; реальный объём и электрические характеристики неизвестны.

Для каждой порции записи:

`порция = min(остаток, 32 − (адрес mod 32))`.

Например, запись 65 байтов с адреса `0x011F` делится на 1, 32 и 32 байта. Исследованный обработчик использует эту границу даже если конкретное устройство допускает более крупную страницу.

Оригинальная функция остатка `0xF22B4` использует цепочку инструкций деления FR и возвращает MDH. В тестах она **заменена математической моделью положительного остатка по 32**, а не исполнена по инструкциям. Само разбиение, построение заголовков и изменение адресов/длины исполнялись оригинальным кодом.

## 2. Состояние, ошибки и уведомления

Байт ответа команды `05` преобразуется в RAM-флаги `0x3E24D`:

- бит ответа 0 → бит RAM `0x80`;
- любой из битов ответа `0x8C` → бит RAM `0x20`;
- исчерпание цикла опроса → бит RAM `0x40`.

По сопоставлению с протоколом EEPROM это похоже на занятость и защиту записи; непосредственно доказаны именно перечисленные битовые преобразования.

`0xD479E` делает до шести опросов. После занятого ответа вызывается задержка с аргументом 2; **единица времени не установлена**.

| Последовательность ответа | Опросов | Флаг `0x40` |
|---|---:|---|
| Готов сразу | 1 | Нет |
| Четыре занятых ответа, затем готов | 5 | Нет |
| Пять занятых ответов, затем готов | 6 | **Да** |
| Шесть занятых ответов | 6 | Да |

Готовность на шестом опросе всё равно даёт флаг ошибки: после выхода код проверяет счётчик. Это установленное граничное поведение, а не автоматически доказанный дефект. Для изменения нужны требования к таймингам реального устройства.

**Уведомление группы 3 отправляется и в проверенном сценарии ошибки опроса.** Оно означает окончание обработки запроса; считать его самостоятельной гарантией успешного чтения/записи нельзя. Внутренний флаг ошибки и проверки вызывающего кода нужно учитывать отдельно.

После последней порции записи в исследованном пути **нет дополнительного опроса состояния и сравнения записанного массива с исходным**. Завершение передачи байтов не доказывает окончание внутреннего цикла EEPROM. Следующий запрос снова опрашивает состояние. Достоверное сохранение данных после отключения питания в этом исследовании не проверялось.

## 3. Что задача 1 читает при запуске

Ветвь `0xC0F1E` вызывает `0xC1164`. Последняя вызывает `0xC11A4`, которая создаёт сообщение:

`00000000 00000000 8000 C000 0400 2000`.

Это чтение с адреса памяти 0 в RAM `0x3C000…0x3C3FF`, длина 1024, уведомление `0x2000` группы 3. Конец диапазона здесь включён.

После получения данных функция `0xC1214` суммирует байты RAM `0x3C000…0x3C37F` **включительно**, с приведением суммы к 8 битам. Возвращаемое значение:

`r4 = (RAM[0x3C37F] − сумма_896_байтов) mod 256`.

Вызывающий код сравнивает r4 с `RAM[0x3C37F]`, что эквивалентно требованию **сумма всех 896 байтов по модулю 256 равна 0**. Это простая контрольная сумма, не CRC.

Кроме суммы, отвергается полностью нулевой или полностью заполненный FF проверяемый диапазон. В `0x3CC9B` отмечаются:

| Бит | Наблюдаемое условие |
|---|---|
| `0x20` | Все проверенные байты нулевые |
| `0x10` | Все проверенные байты FF |
| `0x40` | Одно из двух условий выше либо несовпадение суммы |

При успешной повторной проверке уже установленный `0x40` **в этом фрагменте не очищается**. Дальнейшие последствия флага и все места его сброса пока не разобраны.

Последние 128 байтов прочитанного килобайта — смещения `0x380…0x3FF` — **не входят именно в эту проверку суммы**. Это не означает, что они нигде больше не проверяются.

Назначение каждого поля блока ещё неизвестно. Руководство Nikon D40 действительно связывает EEPROM с регулировочными данными и платой Relay PCB: [VBA15001-R.3701.A, A39](https://www.manualslib.com/manual/844720/Nikon-Vba15001-Black.html?page=67). Привязка конкретных смещений к калибровке батареи, экспозамера или автофокуса этим документом не дана и здесь не объявляется установленной.

## 4. Другие запуски задач из ветви задачи 1

Функция `0xC137C` при начальном `RAM[0x3C371]=0` выполнена без подмены её вложенных функций, с моделью успешных вызовов ОС:

| Запускаемая задача | Аргумент | Условие в проверенной ветви |
|---:|---|---|
| 10 | `0` | Всегда |
| 9 | `0x101` | Всегда |
| 4 | `0xFFFFFF01` | Через `0xC3A78` |
| 2 | `0` | Если бит `0x08` RAM `0x3CC9A` установлен |

Это перечень данной ветви, **не всех зависимостей задачи 1**. Другие значения `0x3C371` и связанные условные запуски требуют отдельного исследования. Назначение задач 2, 4, 9 и 10 не выводится из их номеров.

## 5. Уточнение карты ОС и передачи

Вектор INT `0x40` по `0xFFEFC` указывает на `0xFEECC`. Диспетчер использует signed-индекс кода ×2 относительно `0xFEEC4`, читает signed-16 смещение и прибавляет его к той же базе. Восемь использованных назначений записаны в `data/a_memory_validation.json`.

Обработчики `set/clr/wai_flg` обращаются к таблице `0xFEC80`, `snd/rcv_msg` — к `0xFED24`, `sta_tsk` — к `0xFEB0C`. Это уточняет v9: десять объектов первой таблицы — группы событий, один объект второй — почтовый ящик. Полная диспетчеризация и ошибки ОС не исполнялись; модель INT возвращает явно описанный успешный результат.

Оригинальный callback `0xD4A5E` отдельно проверен на передачу и приём: уменьшается 16-битный счётчик, двигается указатель, принимаемые байты копируются из `0xBB`, после последнего байта вызывается пробуждение задачи 5. Доставка аппаратного прерывания заменена последовательными вызовами callback.

Для массового чтения выполнена настройка `0xD4B0C`: источник `0xBB`, заданный буфер назначения, длина в записях `0x210` и `0x218`, callback `0xD4BA8` по `0x3CC58`. Интерпретация как настройка аппаратного переноса согласуется с кодом; реальная работа этого блока не моделируется. Нулевая длина тоже проходит участок настройки, но её аппаратный смысл не установлен.

Все данные памяти в этих проверках тестовые; физический дамп EEPROM не получен. Совпадение суммы само по себе не доказывает правильность значений калибровки. Все перечисленные проверки прошли. Исходники, EXP01 и прежние интерпретаторы не менялись. Новые файлы: `tools/check_a_memory.py`, `tools/fr_task_machine.py`; результаты — [data/a_memory_validation.json](data/a_memory_validation.json), [VALIDATION_v10.json](VALIDATION_v10.json); карта — [data/a_task_dependencies.json](data/a_task_dependencies.json). Листинги — `evidence/A112_v10_*.asm.txt`.

Для BTSTL использовано руководство производителя Fujitsu FR, [CM71-00101-5E, §7.32](https://manualsdump.com/en/manuals/fujitsu-cm71-00101-5e/119873/142); для возврата остатка в MDH — [руководство FR30, глава 3](https://www.infineon.com/assets/row/public/documents/10/57/infineon-fr30-mb91f127-128-hardware-manual-additionaltechnicalinformation-en.pdf). Эти источники не идентифицируют точную модель процессора D40. Имена вызовов ОС первоначально сопоставлены с [проектом Nikon firmware tools](https://github.com/simeonpilgrim/nikon-firmware-tools); адреса диспетчера и обращение к таблицам дополнительно проверены в самом A 1.12.

## Следующий этап

Теперь можно прослеживать конкретных потребителей 1024-байтного блока и места записи его полей. Нужно также разобрать остальные отправители запросов, сохранение контрольной суммы и реакцию на ошибки передачи. Для обмена A–B предстоит найти другую задачу/обработчик и сопоставить обе стороны. Установка модификации, R330 и восстановление по-прежнему не подтверждены.

Полное назначение задач, все заводские калибровки и протокол обмена ещё не восстановлены. Шкала не меняется: **15 из 48 пунктов, ориентировочно 30%**. Это оценка выполнения плана, не доля понятого машинного кода.

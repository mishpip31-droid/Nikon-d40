# D40 B 1.11: хранение настроек и обработка тоновой кривой

27 октября 2026 года. Дополнение v2 к атласу. Все адреса относятся к оригинальному **BD400111.bin** с SHA-256 `b9df48d461e875dce4ba84da88164af170dfc48ad9f7674859623bad0401032e`. Адрес CPU для обычного ROM равен смещению файла + `0x40000`. Для исполняемого из RAM flash-драйвера ниже явно указан другой адрес.

**Результат:** разобраны журнал постоянного хранения, связь его блоков с Custom и кривыми, развёртка кривой и копирование результата в аппаратные таблицы. Это существенно сужает работу для будущего Cinema 2383, но готового режима и устанавливаемого патча ещё нет. Полная цветовая обработка, восстановление камеры и аппаратные испытания остаются отдельными задачами.

## 1. Найдено настоящее постоянное хранение

Таблица в file `0x9535C` содержит два CPU-адреса: **0x180000 и 0x190000**. Код обрабатывает каждый как сектор длиной `0x10000` — 64 КиБ. В образе B им соответствуют интервалы file `[0x140000,0x150000)` и `[0x150000,0x160000)`. В дистрибутиве оба заполнены FF. По коду они являются хранилищем настроек, **а не свободным местом для патча**. Содержимое дистрибутива не является дампом пользовательских настроек конкретной камеры.

Таблица file `0x95364` содержит 12 записей по 8 байт: RAM-указатель (u32 BE), размер (u16 BE), ещё два нулевых байта. Назначение последнего поля не установлено.

| ID | RAM | Размер | Подтверждённая связь |
|---:|---|---:|---|
| 0 | 0x83CEA524 | 0x14 | Назначение полностью не разобрано |
| 1 | 0x83CED0F8 | 0x48 | Общие настройки; все поля не названы |
| **2** | **0x83CED21A** | **0x12** | **Включает Optimize и параметры Custom** |
| 3 | 0x83CED254 | 0x0E | Копия блока 0x83CE974D при сохранении |
| 4 | 0x83CEB124 | 0x34 | Назначение полностью не разобрано |
| 5 | 0x83CEE068 | 0x44 | Назначение полностью не разобрано |
| **6** | **0x83E89310** | **0x1044** | **Кривая, принимаемая обработчиком PTP 90C6** |
| 7 | 0x83CEE0B4 | 0x10 | Назначение полностью не разобрано |
| **8** | **0x83E882CC** | **0x1044** | **Альтернативная структура кривой в отдельной ветке обработки** |
| 9 | 0x83CEE040 | 0x28 | Назначение полностью не разобрано |
| 10 | 0x83CED248 | 0x0C | Назначение полностью не разобрано |

Наличие двух структур кривой **не означает два доступных пользователю слота**. Их выбор зависит от полей контекста обработки; переносить Cinema во вторую без выяснения её назначения нельзя.

### Формат журнала

Обычная запись: `u16 BE id | u16 BE length | payload | выравнивание до 2 байт`. ID должен быть меньше 12. Длина сверяется с таблицей. Если длина не совпала, запись не обновляет указатель соответствующего блока, но сканер переходит дальше по указанной длине. Это не универсальный защищённый парсер повреждённых данных: все случаи повреждений и выхода за сектор не исследованы.

Запись **`AA 55 | u16 BE generation`** фиксирует текущий набор указателей. Именно этот набор затем используется загрузчиком. Данные после последнего такого маркера не становятся новым подтверждённым состоянием. `FFFF` на месте ID останавливает сканирование. Проверки CRC отдельной записи в изученном сканере нет; контроль длины, маркер завершения и сравнение записанного с прочитанным — разные механизмы, их нельзя называть одной CRC.

| CPU | Роль, установленная по коду |
|---|---|
| **0x6B44C** | Загрузка: сканирует оба сектора, сравнивает поколения, копирует подтверждённые блоки в RAM; при отсутствии блока использует другую копию или ветку начальных значений |
| **0x6B654** | Сканер одного сектора и фиксация указателей на маркере AA55 |
| **0x6B708** | Выбор сектора и способа записи: сравнение, дописывание либо пересоздание |
| **0x6BA04** | Побайтовое сравнение 12 RAM-блоков с сохранёнными; расчёт размера изменений |
| **0x6B8A0** | Дописывание изменившихся блоков и завершающего маркера |
| **0x6B77C** | Стирание сектора и запись всех 12 блоков плюс маркер |
| **0x6B40C** | Обёртка стирания → исполняемый RAM-код **0x83CE8954** |
| **0x6B41E** | Обёртка записи → исполняемый RAM-код **0x83CE89E0** |

Полная новая группа всех 12 блоков с заголовками и маркером занимает **8696 байт**. Дописывание требует места и проверки оставшейся области на FF. Для поколений используется 16-битная разность и порог `0x8000`; это не обычное сравнение целых номеров без учёта переполнения. Прерывание питания во время реальной записи не испытывалось.

Flash-драйвер подтверждает физическую запись: в RAM `0x83CE8B02` видны последовательности `AA, 55, 80, AA, 55, 30` для стирания; в `0x83CE8BE8` — `AA, 55, A0` и запись полуслова. Имеются два варианта адресов команд и проверка завершения. Название и модель микросхемы по этим последовательностям не присваиваются.

### Как в журнал попадают Optimize и Custom

CPU **0x403FA** перед сохранением копирует 9 байт `0x83CE957B → 0x83CED21A`, затем вызывает `0x6B708`. Поэтому старший полубайт режима из `0x83CE957F` становится полем блока ID 2 по смещению **+4** (`0x83CED21E`).

Параметры Custom уже находятся в том же блоке: `0x83CED224` = **+0x0A**, `0x83CED225` = **+0x0B**, `0x83CED226` = **+0x0C**. Значит, для изменения существующих параметров Custom отдельный новый формат хранения не требуется. Для **нового независимого ID Cinema** место ещё не установлено; нельзя объявить соседние биты свободными.

Обратная копия `0x83CED21A → 0x83CE957B` находится в CPU `0x40520…0x4052E`. При загрузке без сохранённой кривой код обнуляет её 0x44-байтный заголовок; это делает активной штатную запасную таблицу. Полная матрица reset и всех моментов вызова сохранения пока не восстановлена.

## 2. Исправлено понимание очереди обновления

Цепочка `0x1468AE → 0x132C3E → 0xA9A50`, найденная в v1, не является непосредственной записью в EEPROM. Это очередь аппаратного обмена:

- Инициализация `0xA995A` создаёт **48** узлов по 12 байт в RAM `0x83CEE504`.
- Таблица команд находится в ROM `0xE482C` / file `0xA482C`, по 16 байт на запись.
- Команда **7** отправляет 9 байт из `0x83CE957B`; callback `0xA9CBA`.
- Команда **8** принимает 9 байт в `0x83CE9572`; callback `0xA9E64` сравнивает/согласует состояние.
- CPU `0xA9724` копирует принятые данные в RAM из дескриптора. CPU `0xA97E6` работает с аппаратными портами и флагами ОС.

Конкретный протокол и идентичность удалённого участника как процессора A ещё не доказаны. Полную таблицу команд сохраняет `data/transport_commands.csv`. Для патча нужно учитывать отдельно синхронизацию рабочего состояния и запись журнала.

## 3. Восстановлен формат кривой, используемый обработчиками

PTP **0x90C6 → CPU 0x8510E** на обычной ветке передаёт приёмщику адрес `0x83E89310` и длину **0x1044 = 4164 байта**. Обратный обработчик **0x90C5 → 0x85072** отдаёт тот же размер, либо запасную структуру из ROM `0xDC250`. Успешное завершение USB-операции само по себе не доказывает немедленную запись flash: прямого вызова сохранения в этом обработчике нет.

Потребители используют структуру так:

| Часть | Размер | Что установлено |
|---|---:|---|
| Заголовок | 0x44 | Первые два байта проверяются на ненулевое значение; смысл остальных полей полностью не восстановлен |
| Таблица | 0x1000 | **2048 полуслов big endian** в RAM, читаемых как значения кривой |

Это установленный формат **для потребителя в памяти**. Полная семантика заголовка, допустимость произвольного пакета и все преобразования транспортного пути ещё не проверены. Подмена первых двух байтов на `01 01` не считается готовым корректным профилем.

CPU **0x4BF06** и **0x4BF58** выполняют одинаковую развёртку. Если любой из первых двух байтов заголовка нулевой, источник — ROM **0xDC294** / file `0x9C294`. Иначе — `0x83E89310 + 0x44`.

```python
for j in range(2047):
    output[2*j] = source[j]
    output[2*j+1] = (source[j] + source[j+1]) // 2
output[4094] = source[2047]
output[4095] = source[2047]
```

Результат — **4096 полуслов / 8192 байта**. Эти две простые функции сами не ограничивают значения 12 битами: проверка с 16-битными входами это подтверждает. Диапазон 0…4095 ограничивается в другом, основном построителе таблицы. Поэтому их нельзя путать.

## 4. Путь до аппаратных таблиц

CPU **0x323C22** строит таблицу в RAM **0x83EB586C**. Поле контекста **+0x466** выбирает ветку; значение **0x17** включает путь пользовательской кривой. Есть отдельная ветка встроенной в контекст таблицы при бите `context[0x1D] & 0x20`, а также ветка второй структуры `0x83E882CC` при сочетании других полей. Обычная ветка пользовательской кривой находится в **0x323EFA**.

После интерполяции выполняется:

```python
output[i] = clamp(interpolated[i] + signed8(correction[9*i + column]), 0, 4095)
```

`column` берётся из `context[0x6AE]`. Шаг 9 задаёт CPU `0x31B6C6`; таблица поправок находится в ROM **0x33692E**, размер 4096 × 9 байт. **В исследуемом оригинале все её значения нулевые.** Код поддержки поправки существует, но не следует приписывать исходному образу ненулевой эффект. Выбор столбца выполняется предыдущими вычислениями, поэтому это поле нельзя прямо использовать как новый ID пресета.

CPU **0x4B41C** вызывает построитель, затем CPU **0x4BEF6** копирует по 4096 полуслов в:

- **0x40018400**;
- **0x4001A400**;
- **0x4001C400**.

Во все три банка идёт **одна и та же таблица**. По этому листингу нельзя уверенно назвать банки R/G/B, установить цветовое пространство, положение относительно матрицы цвета или гарантировать влияние только на JPEG. Но копирование в аппаратную область подтверждено непосредственно инструкциями.

Найден и связанный путь параметров снимка: CPU `0x45692` вызывает `0x4793A` с указателем на структуру +0x2C; туда копируются 8 байт Custom из `0x83CED224`. CPU `0x31ED1A` извлекает биты 4:2 из `context[0x2C]` в RAM `0x83EB3D50`. CPU `0x31F7B6` использует это состояние для выбора кривой, а `0x3234BE` записывает результат в поля +0x466 и +0x6AE. Все промежуточные копии контекстов и переопределения сюжетными режимами ещё не проверены.

## 5. Практический план для Cinema 2383

1. **Тональная часть:** использовать найденный формат 2048 → 4096 и существующий путь Custom как основу исследования. Сначала определить требуемую кривую и её входное/выходное пространство; не переносить значения из неизвестного LUT буквально.
2. **Точный профиль:** содержимое `Cinema_2383.json` в этой итерации получить не удалось. Какие именно операции он содержит, не установлено. Полную эмуляцию Cinema по одному названию обещать нельзя.
3. **Цветовая часть:** если профиль меняет оттенки/насыщенность в зависимости от цвета, общей одномерной кривой это не выразить. Следующая область исследования — матрицы и цветовые таблицы вокруг найденного аппаратного конвейера; поддержка произвольного 3D LUT пока не доказана.
4. **Меню и состояние:** сохранить обычный Custom, выбрать отдельную схему ID и проверить все читатели. Журнал жёстко рассчитан на 12 блоков; увеличение числа или размера требует согласованных изменений сканера, сравнения, записи, загрузки и reset.
5. **Размещение:** исключить оба сектора настроек из кандидатов для кода. Остальные FF-области тоже пока не признаны пригодными.
6. **Проверка:** после воспроизводимого патча — контроль снимков, выключения/включения, USB, reset и восстановления. Сейчас изменённого BIN нет.

## 6. Что проверено и как повторить

```bash
python tools/extract_v2.py /path/to/BD400111.bin /path/to/atlas_output
python tools/check_storage_curve.py /path/to/BD400111.bin
python tools/test_atlas.py /path/to/originals
python tools/check_selector.py /path/to/BD400111.bin
```

Новый интерпретатор исполняет **оригинальные байты** трёх функций: `0x4BF06`, `0x4BF58`, `0x6B654`. Он ограничен наблюдаемыми инструкциями, учитывает delay slots, останавливается на неизвестной инструкции/неотображённой памяти и не подключается к камере.

**48 прогонов кривой:** две функции × четыре сочетания флагов × шесть наборов данных, включая границы, немонотонные и полные 16-битные значения. Проверяются точные 4096 результатов, сохранность входа и защитных байтов вокруг выхода.

**20 прогонов сканера:** два адреса сектора × десять сценариев: пустой сектор, незавершённая запись, один/два маркера, незавершённый хвост, неверная длина, недопустимый ID, поколение FFFF, пустой подтверждённый набор, все 12 блоков. Проверяются подтверждённые указатели, номер поколения, сохранение регистра и стека.

Это проверка ограниченных фрагментов на искусственных данных. Стирание/программирование flash, весь JPEG-конвейер, реальное отключение питания и установка обновления **не исполнялись**. 22 новых листинга и хеши диапазонов лежат в `evidence/` и `data/v2_evidence_ranges.json`; результаты команд — в `VALIDATION.json`.

# Обновление Nikon D40: результаты разбора v7

28 октября 2026 года. Разбирается точный оригинал **B 1.11** с SHA-256 `b9df48d461e875dce4ba84da88164af170dfc48ad9f7674859623bad0401032e`. Для обычного ROM здесь `CPU = file + 0x40000`; для скопированного служебного кода используется отдельно указанное отображение RAM.

## Главный результат

Восстановлены поиск файла, предварительная проверка его содержимого, расчёт CRC и последовательность команд записи B. **Содержимое EXP01 проходит найденные предварительные проверки и проверку CRC.** Проверки выполнены на компьютере, с заменой файловой системы на память. Физическая установка, перезапуск, съёмка и аварийное восстановление остаются непроверенными.

Прежнее опасение о неизменённом номере B 1.11 уточнено: **в разобранном предварительном проверяющем коде нет требования увеличивать номер версии**. Это уже подтверждено исполнением, а не только просмотром строк. Однако это не исследование всех возможных условий аппаратной системы.

Важное ограничение: имя `D40_Cinema2383_EXP01_NOT_CAMERA_TESTED.bin`, с которым выдан экспериментальный образ, **не соответствует шаблону поиска камеры**. Испытание содержимого отдельно моделировало открытие файла с обычным подходящим именем. Этот отчёт не предлагает переименовать файл и сразу установить его.

## 1. От меню до предварительной проверки

| Узел | Адрес CPU | Что делает |
|---|---|---|
| Инициализация экрана Firmware version | `0x140FE4` | Вызывает проверку доступности обновления, выбирает один или два доступных пункта |
| Выбор кандидата | `0xAB5CC` | Обнуляет тип кандидата, проверяет условия входа, сначала ищет B, затем при отсутствии совпадения — A |
| Условия входа | `0xAB646` | Проверяет результат `0x40DDA`, флаг RAM `0x83CE971E & 0x40`, байт `0x83CEB168` и результат системного вызова; физический смысл всех условий ещё не установлен |
| Поиск имени | `0xABE82` | Перебирает записи корня `A:\`, сравнивает имя с шаблоном |
| Предварительная проверка B | `0xABBFE → 0xABCE4` | Проверяет размер, открывает файл, читает идентификатор и префикс версии |
| Предварительная проверка A со стороны B | `0xABC6E → 0xABE28` | Допускает размеры `0x40000` или `0x40002`, читает первые шесть байт |
| Действие Yes | `0x1416DC` | Подготавливает экран и состояние, вызывает основной путь обновления `0xAB88E` |

`AB646` и весь граф пользовательского интерфейса не исполнялись целиком с настоящими внешними подсистемами. Проверка файла не равна проверке достаточности заряда, готовности карты и всех состояний устройства.

Если найдено имя B, его проверка используется сразу; переход к поиску A происходит при отсутствии совпадения имени B. Нельзя предполагать, что неправильный B-файл будет автоматически пропущен ради A.

## 2. Какое имя ищет камера

Строки в ROM:

- `0xE4BB8`: `AD40????.BIN`;
- `0xE4BC8`: `BD40????.BIN`.

Исполнен оригинальный сравнивающий код с моделью перечисления каталога. Сравнение не чувствительно к регистру ASCII; каждый `?` принимает один ненулевой символ, не обязательно цифру. Длина должна совпасть с шаблоном. Проверены, среди прочего, стандартное имя, строчные буквы, короткое/длинное имя, буквы вместо четырёх символов и длинное экспериментальное имя.

Выбирается **первое совпадение при перечислении каталога**, а не файл с самым большим номером в имени. Это не гарантирует конкретного порядка реальной файловой системы.

## 3. Предварительная проверка B

1. Поле размера в записи каталога должно быть **ровно `0x3D0000`, то есть 3 997 696 байт**.
2. Из file `0xAFBF4` читается 32-битный адрес строки идентификации. Из него вычитается `0x40000`, после чего читаются 32 байта файла.
3. Строка сравнивается с установленным оригиналом: **`Q330FirmwareSignature`**, включая достижение нулевого терминатора. Это текстовый идентификатор, **не криптографическая подпись**.
4. Из file `0xAFBF0` читается адрес строки версии; после перевода в смещение файла читаются девять байт.
5. Префикс сохраняется для дальнейшего использования; тип кандидата в RAM `0x83CEE980` становится 1, функция возвращает успех.

В оригинале указатели ведут на file `0x95520` и `0x95538`. Прочитанный префикс — `Ver.1.11A`. Эта строка находится именно в B-файле; буква в ней не использовалась для определения части A/B.

В проверочных копиях **в памяти** префикс менялся на `Ver.1.00A`, `Ver.1.11A`, `Ver.9.99A`, `XXXXXXXXX`. Все четыре прошли этот предварительный этап. Проверка CRC на нём не выполняется; принятие произвольного префикса не означает, что такой файл пригоден для обновления или отображения в меню.

Отрицательные проверки: четыре неверных размера, изменённый идентификатор, ошибка открытия, ошибки каждого из четырёх перемещений/чтений и четыре неполных чтения. Все 18 случаев отвергнуты оригинальным кодом. Файловые операции `0x6C25E`, `0x6C40A`, `0x6C2E2`, `0x6C2A0` заменены явно описанной моделью; сама проверяющая логика исполнена без подмены.

## 4. Проверка CRC перед записью

Основной путь B в `0xAB88E`:

1. Повторяет условия допуска через `0xAB646`.
2. Через `0xAB97C` читает весь файл в RAM начиная с `0x81000000`; требует успеха чтения и точного числа полученных байтов.
3. Вызывает `0x44CCC` для **всех `0x3D0000` байтов, включая два конечных байта CRC**.
4. Продолжает только при нулевом результате.
5. Выполняет синхронизацию через `0xAB9F8`, сохраняет настройки вызовом `0x403FA` и переходит через `0x6B430` в RAM-функцию записи.

CRC-функция использует 256 полуслов из ROM `0xC3A88`. Восстановленная формула:

```text
crc = 0
для каждого байта:
    crc = ((crc << 8) XOR table[(crc >> 8) XOR byte]) AND 65535
```

Все 256 элементов таблицы совпали с полиномиальным расчётом CRC16/XMODEM (`0x1021`). Оригинальная CPU-функция исполнена на 265 входах, включая все однобайтовые значения, пустой вход, `123456789` и случайные данные до 8192 байт. На полных оригинале и EXP01 выполнена точная целочисленная модель этого цикла и независимый `binascii.crc_hqx`: остаток в обоих случаях **0**. Однобитовая порча даёт ненулевой результат.

Полные четырёхмегабайтные образы не прогонялись по инструкции в этом тесте; это отдельно отмечено в JSON. Аппаратная синхронизация и последующая запись не подменяются утверждением о «полной эмуляции камеры».

## 5. Какие области записываются

`0x6B430` вызывает **RAM `0x83CE86CE`**. Код берётся из file `0x11CBE2` и входит в установленный ранее стартовый диапазон копирования. Для его листинга `RAM = file + 0x83BCBAEC`.

Исполнен участок управляющей функции `0x83CE877C…0x83CE8892`. Сама функция сравнения тегов `0x83CE8E96` также исполнялась. Низкоуровневые стирание и запись `0x83CE8954`/`0x83CE89E0` **заменены регистрацией команд и заданными результатами**, без моделирования flash-чипа.

| Записываемый диапазон CPU/flash, конец не включён | Соответствующий диапазон B-файла | Условие |
|---|---|---|
| `0x160000…0x170000` | `0x120000…0x130000` | Только при несовпадении обоих тегов обоев |
| `0x120000…0x160000` | `0x0E0000…0x120000` | Обычный путь |
| `0x1B0000…0x410000` | `0x170000…0x3D0000` | Обычный путь |
| `0x040000…0x0F0000` | `0x000000…0x0B0000` | Обычный путь, программируется последним |

Для условного участка сравниваются первые 16 байтов установленного блока с входящим тегом `NIKOND40_WPVER01` и маркером `NIKOND40_WP_USER`. Совпадение с одним из них сохраняет этот участок. Диапазоны между перечисленными областями не записываются этим кодом; это **не доказательство, что они свободны для дополнений**.

Перед программированием выполняются стирания соответствующих областей. В частности, участок с векторами B стирается раньше, чем заново программируется последняя группа. Это не схема атомарного переключения между двумя полностью сохранёнными образами.

Проверены пять сценариев: сохранение обычных обоев, сохранение пользовательских обоев, замена неизвестного блока, отказ стирания и отказ программирования. При постоянном отказе выполняется до трёх попыток. **Это повтор операции, не восстановление предыдущей прошивки.**

Все **4435 изменённых байтов EXP01**, включая код, кривую и CRC, входят в обычные программируемые диапазоны. Это подтверждает адресное покрытие изменений, но не физическую успешность записи.

## 6. Что это означает для проекта

- Неизменённый номер B 1.11 сам по себе не блокируется найденным предварительным проверяющим кодом. Обновлять строку версии для обхода этой проверки не требуется.
- Содержимое EXP01 соответствует найденным требованиям размера, идентификатора и CRC. Сам образ в этом исследовании не менялся.
- Длинное экспериментальное имя не будет найдено рассматриваемой функцией. Это отдельный вопрос от содержимого.
- Для «маленькой прошивки с одним режимом» простое сокращение файла нарушит проверку размера. Упрощение меню и уменьшение физического файла — разные задачи; рабочая сокращённая версия ещё не создана.
- Безопасная установка и аварийное восстановление всё ещё не подтверждены. Не разобраны полностью условия допуска, физический протокол flash, аппаратная синхронизация с другой подсистемой и состояние после обрыва питания.

## Воспроизведение

```sh
python tools/check_updater.py /path/BD400111.bin --original_A /path/AD400112.bin --experimental /path/D40_Cinema2383_EXP01_NOT_CAMERA_TESTED.bin --output /path/updater_validation.json
```

Параметр `--experimental` необязателен. При его наличии принимается только точный хеш EXP01 из отчёта; другой патч не проверяется автоматически как эквивалентный. Отчёт пакета: `data/updater_validation.json`. Листинги: `evidence/B_update_*.txt`. Скрипт не подключается к камере и не записывает прошивки.

Официальная [инструкция Nikon D40 A/B 1.11](https://downloadcenter.nikonimglib.com/en/download/fw/119.html) подтверждает использование корня SD-карты, отдельную установку A/B и запрет выключения во время обновления. Она относится к штатным файлам и не подтверждает безопасность EXP01.
